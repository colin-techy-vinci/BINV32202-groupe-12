Parcours d'affichage des offres

Gesta sépare l'interface React, l'API Express et la persistance SQLite. Cette page décrit le chemin d'une requête de liste d'offres, depuis le composant React jusqu'aux lignes SQL, puis le retour vers l'écran.

1. Vue d'ensemble de l'architecture

Le dépôt est un workspace npm composé de frontend/ et backend/. Le frontend est une application React servie par Vite. Le backend est une API Express en TypeScript. SQLite est utilisée par better-sqlite3, avec des migrations SQL versionnées.

En développement, le navigateur appelle /api/.... Le proxy configuré dans frontend/vite.config.ts transmet ces appels à l'API sur le port 3000 et supprime le préfixe /api.

2. Parcours complet d'une liste d'offres

1. Composant React : frontend/src/pages/OffersPage.tsx reçoit l'utilisateur et le jeton, appelle useOffers, puis rend les états de chargement, d'erreur, de liste vide ou le tableau.
↓
2. Hook : frontend/src/hooks/useOffers.ts déclenche le chargement dans un useEffect. Il annule la requête lors du démontage, conserve la liste en état et traite les erreurs 401 via onUnauthorized.
↓
3. Service frontend : frontend/src/services/offers.service.ts envoie un GET /api/offers avec le jeton dans l'en-tête Authorization. readJson vérifie le statut HTTP et isOfferList valide la forme JSON.
↓
4. Proxy Vite : frontend/vite.config.ts route /api/offers vers http://localhost:3000/offers.
↓
5. Authentification Express : backend/src/app.ts branche authenticate sur les routes d'entreprises et d'offres. Le middleware relit l'utilisateur en base à partir du jeton ; les rôles ne sont donc pas acceptés depuis le client.
↓
6. Route et autorisation : backend/src/controllers/offers.controller.ts protège GET /offers avec authorize(canListOffers). Un contact qui n'est pas déposant reçoit 403. Le contrôleur transmet l'utilisateur au service et convertit chaque résultat en DTO.
↓
7. Règle de visibilité : backend/src/services/offers.service.ts construit le filtre serveur selon le profil : aucun filtre additionnel pour un administrateur, status = PUBLISHED pour un étudiant, ou depositorContactId = utilisateur.id pour un déposant.
↓
8. Repository et SQLite : backend/src/repositories/offers.repository.ts lie les paramètres du filtre à une requête SQL sur offers. Elle joint companies, academic_years et periods, puis trie par année académique décroissante et date de création décroissante.
↓
9. Modèle et DTO : backend/src/mappers/offer.mapper.ts transforme la ligne SQL OfferDbo en objet métier puis en OfferDto. Le DTO expose seulement l'identifiant, le titre, l'entreprise, l'année, la période et le statut.
↓
10. Rendu : useOffers stocke le tableau, puis OffersPage passe les offres à frontend/src/components/OfferTable.tsx. Le composant affiche la période avec les libellés français de frontend/src/utils/labels.ts.

Requête SQL actuelle

SELECT o.id, o.title, o.description, o.status,
       o.company_id, c.short_name AS company_short_name,
       o.depositor_contact_id,
       ay.label AS academic_year_label, p.code AS period_code,
       o.created_at, o.updated_at
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC

3. Données et responsabilités

CoucheResponsabilitéContrat important
React / page Orchestrer l'affichage et les états UI. Ne décide pas quelles offres un utilisateur a le droit de voir.
Hook / service Charger les données et valider le JSON. Le jeton est envoyé tel quel, sans préfixe Bearer.
Contrôleur / middleware Appliquer l'accès HTTP et convertir la réponse. Les erreurs suivent { "error": { "code", "message" } }.
Service Appliquer les règles de visibilité métier. Les règles sont nommées dans permissions.ts.
Repository Exécuter la requête SQL et retourner des DBO. Les paramètres SQL sont liés, pas concaténés.
SQLite Conserver offres, années et périodes. periods appartient à une année via une clé étrangère composite.

4. Ajout d'un filtre par période

Le filtre devrait être appliqué côté serveur afin de conserver les règles de visibilité et de ne pas charger au client des offres que le filtre devrait seulement masquer. Le code de période existant est P1, P2 ou OTHER.

FichierÉvolution probable
frontend/src/pages/OffersPage.tsx Ajouter le contrôle de sélection et conserver la période choisie dans l'état de la page.
frontend/src/hooks/useOffers.ts Recevoir la période comme dépendance, la transmettre au service et recharger lors de sa modification.
frontend/src/services/offers.service.ts Construire /api/offers?period=P1 (ou omettre le paramètre quand aucun filtre n'est sélectionné).
frontend/src/models/offer.ts Réutiliser PeriodCode ou définir le type du filtre si l'API distingue valeur absente et valeur sélectionnée.
frontend/src/utils/guards.ts À vérifier : la réponse contient déjà period, mais tout nouveau format de filtre doit y être validé.
backend/src/controllers/offers.controller.ts Lire et valider le paramètre period, refuser les valeurs inconnues et transmettre un filtre typé.
backend/src/services/offers.service.ts Combiner le filtre de période avec le filtre de visibilité propre au profil.
backend/src/repositories/offers.repository.ts Ajouter periodCode à OfferFilter, aux paramètres liés et à la clause WHERE, probablement sur p.code.
backend/src/models/offer.ts Le type PeriodCode existe déjà ; il sert de contrat partagé pour la valeur filtrée.
backend/src/db/migrations/001_initial.sql Normalement inchangé : la colonne period_id et la table periods existent déjà. Une migration est nécessaire seulement si le contrat de données change.
backend/tests/offers.test.ts Ajouter des tests de validation, de filtrage par période et de combinaison avec les profils admin, étudiant et déposant.
frontend/tests/OffersPage.test.tsx Vérifier l'affichage du contrôle, la requête envoyée, le rechargement et l'état vide d'une période.
backend/API.md Documenter le paramètre, les valeurs acceptées et la réponse 400 en cas de période invalide.
Point de conception : le filtre de période doit être ajouté au filtre métier existant, et non remplacer le filtre de statut ou de déposant. Un étudiant doit donc continuer à ne recevoir que les offres publiées, même lorsqu'il demande P1.

5. Tests de référence

  • backend/tests/offers.test.ts couvre l'authentification, les droits et la visibilité par profil.
  • frontend/tests/OffersPage.test.tsx couvre le rendu, les libellés, les erreurs 403 et l'expiration de session.
  • backend/tests/db/constraints.test.ts couvre notamment la cohérence entre période et année académique.
